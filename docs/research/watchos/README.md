# Calling on watchOS

## Findings

A Swift watch app is a plausible long-term client, but a working standalone incoming call is **not established**. CallKit and LiveCommunicationKit are present on watchOS; the published LiveKit Swift/WebRTC distribution does not currently include watchOS. Apple documentation also conflicts on VoIP push availability. Treat direct incoming-call delivery and the media path as open questions, not commitments.

The availability below was checked against the Xcode 27.1 watchOS SDK declarations, not against a physical watch. An API declaration establishes compile-time availability, not delivery, entitlement, audio routing, or App Store acceptance.

| API | watchOS availability | Evidence and qualification |
| --- | --- | --- |
| `CXProvider`, CallKit call actions and incoming-call reporting | 9.0 | The SDK headers mark `CXProvider` and its delegate watchOS 9.0. Apple announced CallKit VoIP call controls on Apple Watch in [WWDC22](https://developer.apple.com/videos/play/wwdc2022/101/) and documented a watchOS 9 [CallKit SDK issue](https://developer.apple.com/documentation/watchos-release-notes/watchos-9-release-notes). `CXProvider.reportNewIncomingVoIPPushPayload` is unavailable on watchOS in the installed SDK; use of another API does not establish a push delivery path. |
| `PKPushRegistry`, `PKPushType.voIP` | 9.0 for the VoIP type in the installed SDK | The SDK exposes the type on watchOS 9.0, but Apple's [APNs push-type table](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns) says the `voip` push type is unavailable on watchOS. The generic [PushKit overview](https://developer.apple.com/documentation/pushkit) does not resolve that conflict. Do not promise a direct VoIP wake or incoming ring until Apple clarifies the documentation and an actual watch delivery test succeeds. |
| `ConversationManager`, `ConversationManager.Configuration` and conversation actions in LiveCommunicationKit | 10.4 | The installed `LiveCommunicationKit.swiftinterface` declares watchOS 10.4 availability. Availability of these symbols does not establish equivalence with CallKit, delivery from APNs, or support for any particular media transport. See [LiveCommunicationKit](https://developer.apple.com/documentation/livecommunicationkit). |
| `AVAudioSession.Category.playAndRecord`, `.record`, `.playback`, `.multiRoute`; `AVAudioSession.Mode.voiceChat`, `.videoChat` | 2.0 in the installed headers | Apple describes [`playAndRecord`](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playandrecord) and [`voiceChat`](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/voicechat) for two-way VoIP. Declaration availability does not guarantee that a category, mode, or route works on every watch: check [`availableCategories`](https://developer.apple.com/documentation/avfaudio/avaudiosession/availablecategories) and test real hardware. `activate(options:completionHandler:)` is available from watchOS 5 for the documented [long-form playback flow](https://developer.apple.com/documentation/avfaudio/avaudiosession/activate(options:completionhandler:)); it should not be assumed to be the call activation flow. Some iOS audio tuning APIs, including preferred sample rate and I/O buffer duration, are explicitly unavailable on watchOS in the installed headers. |

A local `swiftc -typecheck` against the watchOS 10.4 simulator target successfully imported all four frameworks and referenced `PKPushType.voIP`, `CXProvider`, `ConversationManager`, `.playAndRecord`, and `.voiceChat`. This checks declarations only. In particular, it cannot resolve the APNs discrepancy.

## Network and media constraints

Apple classifies HTTP(S) `URLSession` requests as high-level networking. Network framework, `NSStream`, direct TCP or UDP, `URLSessionStreamTask`, and `URLSessionWebSocketTask` are low-level networking. On watchOS, low-level networking is allowed while an audio app is actively streaming audio (watchOS 6 and later), while a VoIP app runs a CallKit call (watchOS 9 and later), or for the specific DeviceDiscoveryUI use case. Outside those cases it is blocked. Apple says BSD sockets do not work for watchOS networking in any circumstances. See [TN3135](https://developer.apple.com/documentation/technotes/tn3135-low-level-networking-on-watchos).

[LiveKit signaling](https://docs.livekit.io/reference/internals/client-protocol/) uses a WebSocket and WebRTC media uses low-level networking. It is therefore unsafe to assume a persistent signaling connection before a qualified call or after it ends. A port also needs a watch-compatible networking implementation, including any code that uses BSD sockets; permission for low-level networking during a call is not enough to make a binary built for other platforms work. Apple's [WWDC19 audio session](https://developer.apple.com/videos/play/wwdc2019/716/) describes using HTTP requests for initial data before audio activation. How to establish and recover the signaling and call state within the permitted window requires a watch-specific design and measurement.

The [LiveKit Swift package manifest](https://github.com/livekit/client-sdk-swift/blob/main/Package.swift) lists iOS, macOS, Mac Catalyst and tvOS, not watchOS. Its published [WebRTC XCFramework](https://github.com/livekit/webrtc-xcframework) lists no watchOS device or simulator slice. The published stack therefore cannot be treated as a supported watch dependency. This does not prove WebRTC itself can never be ported. Possible research directions include a separately validated watch-compatible media implementation and server bridge, or a companion-assisted experience. None is established here as a production-ready replacement; each needs interoperability, latency, battery, route, and network testing. LiveKit describes [SIP participants](https://docs.livekit.io/reference/telephony/sip-participant/) as room participants, but that alone does not supply a watch media client.

## Standalone and companion behavior

An [independent watch app](https://developer.apple.com/documentation/watchos-apps/creating-independent-watchos-apps) can operate without its iPhone app installed, but needs its own authentication and data access. A watch can use a paired phone, known Wi-Fi, or its own cellular connection when available; connectivity depends on the watch and its configuration. See Apple's [watch networking overview](https://developer.apple.com/documentation/watchos-apps/keeping-your-watchos-app-s-content-up-to-date).

A standalone watch needs its own registration and delivery path when the phone is away. Apple supports [direct watch notifications and forwarded phone notifications](https://developer.apple.com/documentation/watchos-apps/enabling-and-receiving-notifications), but regular notification delivery is not a substitute for a demonstrated VoIP wake, system-call presentation, and timely media connection. [Background notifications](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app) can be delayed or dropped. A companion can offer phone-side calling and notification forwarding while both devices are available; it cannot guarantee calls on a watch when the phone or its network path is absent. The APNs discrepancy above must be resolved before committing to standalone incoming calls, including on cellular watches.

## Core boundary and CI proposal

Keep call models, policy, and protocol logic independent of UIKit, Expo/React Native, iOS-only lifecycle assumptions, and unavailable audio or provider methods. Put platform presentation, push registration, audio routing, and media behind platform-specific adapters; guard each API at its actual platform and OS availability. The existing [UIKit import](../../../Sources/VoIPSDK/VoIPApplication.swift) is already iOS-conditional; the [Expo app delegate](../../../Expo/apple/VoIPAppDelegateSubscriber.swift) is iOS-specific. The [package manifest](../../../Package.swift) currently declares iOS 17.4 rather than a watchOS deployment contract.

A local Xcode 27.1 build of the current `VoIPSDK` scheme for the generic watchOS Simulator succeeded for arm64 and x86_64 with signing disabled. It emitted two Swift concurrency warnings; this was a compile check, not a call or media test. Add a CI job using the following build, then explicitly choose and declare a watchOS deployment target when support is a product commitment:

```sh
xcodebuild -scheme VoIPSDK -sdk watchsimulator \
  -destination 'generic/platform=watchOS Simulator' \
  CODE_SIGNING_ALLOWED=NO build
```

Build the full watchOS dependency graph so the check catches unavailable dependencies in code compiled for watchOS. It does not compile iOS-only conditional branches, so retain separate iOS checks. Add watch-specific unit tests once a supported watch adapter exists; a green build must not be presented as end-to-end calling support.

## What the simulator can establish

The simulator can compile the SDK, exercise deterministic models and adapter tests, and run watch UI interactions. Apple also describes [simulated notification payloads](https://developer.apple.com/documentation/watchos-apps/testing-custom-notification-interfaces) and [watch simulator controls](https://developer.apple.com/documentation/xcode/interacting-with-your-app-in-the-watchos-simulator). Those tests do not establish actual APNs delivery, cold-start incoming calls, real audio routes, battery behavior, cellular reachability, or background execution. In particular, [TN3135](https://developer.apple.com/documentation/technotes/tn3135-low-level-networking-on-watchos) says the simulator always permits low-level networking, so a simulator pass cannot qualify the watch networking restrictions. Those questions need physical-watch testing after the delivery and media designs are selected.
