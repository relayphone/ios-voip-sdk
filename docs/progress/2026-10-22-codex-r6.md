# R6: shipping tamper controls (prepared October 22, 2026)

## Change and acceptance

**Proposed acceptance:** after a fresh current-runtime discovery capture passes,
`python3 discovery/check_shipping_controls.py <output-directory>` must pass its
positive captures and reject all 32 materialized semantic mutations for their
specific reasons. `python3 discovery/check_cli_controls.py` must pass its positive
command and reject all 12 malformed package/session/response/timeout cases.
The integrated CI run must supply the native evidence before R6 is accepted.

The shipping controls call the same strict `summarize.validate` entry point used
by the native harness, with `runtime.identity` version `0.1.0` required in both
runtime and push captures. They cover the post-end-unmute allowance, system mute
echo inventory and values, journal identity/sequence/profile/action/transaction
bindings, and group targets. Receipt trace and journal hashes are recomputed
after mutations, so checksum rejection cannot hide a missing semantic rule.

The semantics and generation validators now expose callable validation functions
behind main guards; command-line checks retain their assertions. Their negative
controls mutate controller results, action identities, observer state, missing or
duplicate lifecycle boundaries, a false check result and stale unmute production.

CLI controls execute the actual `Tools/cksim` subprocess with a synthetic package
and a temporary fake `xcrun` mailbox responder. Every failure checks its expected
diagnostic; rejected packages and sessions must produce no mailbox request.
They do not use Apple tools, simulator environment variables, loader installation
state or a changed home directory. CLI bytes are identified in the result.

## Local evidence

**Measured, synthetic local tests:**

- 35 shipping/semantics/generation checks passed: three positive captures and
  32 semantic mutations.
- 13 CLI controls passed: one positive and 12 negative controls.
- The existing 49 harness controls and 11 image-identity controls passed.
- Python compilation and `git diff --check` passed.
- A deliberate local replacement of `summarize.shipping_journal` with a no-op
  made the new controls fail at `runtime-journal-sequence` with an accepted-
  tampering diagnostic, confirming that the shipping branch is exercised.
- Injecting an unrelated genuine-scenario failure into derived summarize
  results is rejected immediately, even when the intended runtime error is
  present. The control harness matches only the target scenario's diagnostic.

The development input is an **explicitly synthetic derivative**, held only in
ignored `discovery/out/r6-synthetic-development/`, of the saved artifact from
[CI run 39680771297](https://github.com/ziahamza/ios-voip-sdk/actions/runs/39680771297).
Its pre-R1 completion-thread fields were changed to `main: true`; missing R5
loaded-image digest fields were copied from its old manifest. Trace receipt
hashes were recomputed. The original artifact was not changed. These field
changes are fixture construction, **not a new runtime measurement**, and are
not native acceptance evidence. No binary or transformed capture is committed.

The development source manifest SHA-256 is
`fc5bb379bb78b9428ba2eb79b79cfddcc96085dca90cf1e74c193b5fa206502a`.
The runner prints source manifest and trace hashes to bind each future controls
result to its actual input capture.

## Integration and open work

The CLI controls are wired into the CI preflight, and shipping controls run after
all native scenario outputs exist, saving their JSON result with the artifacts.
A fresh integrated run still needs recording in the PR description. The outer
CLI-test process budget is 20 seconds after a busy-host startup exceeded five;
the CLI's independent no-response deadline remains 0.1 seconds. The new shipping runner copies JSON
and text metadata, including the OS/toolchain inputs prepared by R8, into each
tampered fixture. It reads the capture's runtime package through a read-only
test symlink; it does not mutate the original capture or package.

R3's device characterization remains outside this change. R7 owns device-derived
deadline and D5 expectations. No Tools source or runtime implementation is changed.
