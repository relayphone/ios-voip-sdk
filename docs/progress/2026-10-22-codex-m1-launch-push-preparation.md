# M1 native launch and push preparation

**Proposed:** this component adds the launch-owned native receiver and policy. M1's native push journey, cold-launch deadline acceptance and real PushKit reporting check remain pending. Package, podspec, Expo subscriber and bridge wiring belong to the integration change.

**Measured:** the source-bound [receipt](../verification/2026-10-22-sdk-m1-launch-push/receipt.json) contains passing core/push host tests and Swift 6 module compiles for iOS 17.4 Debug/Release and watchOS 10.4 source compatibility. No app was linked or run, and no simulator/device was used. Device/watch compilation exercises `SWIFT_PACKAGE` imports with a temporary platform module map. Existing LCK-manager concurrency warnings remain visible.

`VoIPApplication.start(configuration:)` creates the process client and one `PushService`, then starts the Objective-C registry owner during application launch. Repeated identical configuration reuses both; a registration error can retry without another manager. `startFromBundle(_:)` reads the `VoIPSDK` Info.plist dictionary, including the core configuration, simulator preference, ringtone and bundled icon. Missing icons use a static diagnostic and the system icon. Conflicting late configuration throws rather than changing an existing runtime/manager.

**Proposed:** `ConversationClient.shared` now installs the DEBUG provider monitor itself. The order is simulator activation, monitor installation, begin owned creation, manager creation, end owned creation. Native Swift users receive the guard without Expo. The public insertion callbacks from the earlier preparation are removed. `SimulatorSupport.configure(enabled:)` selects the preference before the first activation request.

**Proposed wire policy:** PushKit dictionaries are decoded synchronously into Sendable values before a Task. `incomingCall` presence wins even malformed; only its absence permits `incoming_call`. Flat and JSON-string invitation envelopes are rejected. Required IDs remain nonempty strings; wrong/missing video defaults false; optional invalid dates are dropped; metadata remains an opaque JSON object. FCM `messageType: callEnded` decodes its JSON-string body, with unknown/missing reason mapped to remoteEnded. `PushWire.decodeIncomingInvitation` and `decodeCallEnded` also serve inner-object native/Expo reports.

Every valid invitation calls the PushKit source reporting path, including metadata-false deliveries. Optional malformed pushes finish without reporting. Required malformed pushes synthesize an unknown invitation, report it, immediately report ended/failed, then finish. Optional callEnded applies its target termination. Required callEnded applies the target termination plus the unknown incoming/end fallback so the incoming API is still attempted. These are proposed reporting policies; they do not establish what the device's required-report check accepts. Static diagnostics never include tokens, payloads or arbitrary error descriptions. The Objective-C completion guard remains responsible for exactly-once completion.

`PushService.tokenState` is cached, revisioned and nullable. Updates/invalidation are serialized through reentrant observers; duplicate values do not advance the revision. Encoding always includes `token`, including explicit `null`. `observeToken` immediately hydrates a late subscriber. `receiveRemoteMessage` routes recognized FCM callEnded messages and reports whether a live/in-flight SDK target accepted the end, without logging. The underlying `receiveCallEnded` is now discardable-result Bool. Framework-free state/event models moved into `ConversationModels.swift` for bridge host controls.

**Measured integration red:** a combined Engine+SDK simulator compile exposed private Engine `PendingAction` colliding with SDK `PendingAction`. The retained red log binds the current sources. A second compile passed after mechanically renaming four occurrences in an isolated Engine copy to `RuntimePendingAction`. This component leaves Engine unchanged; root applies the production private rename and must verify the actual Expo build. No runtime behavior or R3 lifecycle change is proposed by that rename.

**Measured review:** independent spec and standards reviews found no blockers in the launch/push code. Host controls cover canonical precedence, aliases, invalid envelopes/IDs/video/date/timezone/metadata, required-report policy, FCM end reasons, token hydration/invalidation/null encoding/reentrancy and simulator preference locking. One negative date control first reproduced Foundation accepting an out-of-range timezone; explicit component ranges fixed it. Native acceptance still needs to bind async LCK reports to the runtime's push receipt: the existing thread-local correlation does not automatically survive the Task boundary, and no speculative runtime change was made here.
