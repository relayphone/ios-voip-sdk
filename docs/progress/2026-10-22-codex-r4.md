# R4: loader recovery and test-host loading (October 22, 2026)

## Acceptance target

Apps without the SDK use process-local test-host injection by default. A saved
simulator-wide installation can be repaired after deleting its runtime package,
without discarding another injector's changes. This prepares START-HERE §4.A R4;
the offline check is integrated into CI; an owned simulator acceptance remains
pending before a PR is accepted.

## Prepared change

- `cksim repair` reads the existing ownership file independently of the runtime
  package. It removes the exact saved loader entry from `DYLD_INSERT_LIBRARIES`,
  preserves unrelated entries, and restores recognized `CKSIM_*` values.
- All keys are checked before writes. Ambiguous external values and extra exact
  loader duplicates refuse with the affected key and ownership-file path.
- Failed installs and failed repairs retain recovery state. Successful repair
  deletes that state; repeating it is a no-op. `repair` and `uninstall` do not
  require `--bundle`. Every CLI `simctl` subprocess has a 60-second deadline.
- The runtime documentation makes generated `.xctestrun` host environments the
  default and distinguishes a UI-test runner from its app under test. Global
  `install` remains an explicit option with deletion and recovery instructions.

## Proposed hosted native acceptance

`discovery/run_repair.py` measures one actual CLI install/repair sequence on its
own disposable simulator. It builds a current package plus signed unrelated
injectors, preserves inherited library entries, deletes the package, repairs via
the source CLI, checks exact remaining libraries and restored keys, repeats repair
idempotently, restores the original global environment, and deletes the simulator
and build. All subprocesses have deadlines and owned process groups; timeout or interruption
kills and reaps the group without waiting for descendant-held pipes. A measured
synthetic interruption control terminated a fake build and its sleeping descendant,
removed the build and wrote a failing receipt in 0.014 seconds, without a simulator.
Its receipt binds source, CLI,
fixture, package and helper hashes to the selected simulator OS; inherited
values are represented only by hashes. Discovery CI runs it after the ABI cases
on the Xcode 26.6 lane and uploads a separate repair artifact.

No hosted native repair acceptance is claimed until that step passes. The local
preparation limitation does not qualify repair on iOS 27.0. This fixture measures
launchd recovery; it does not launch an app or qualify a new host's generated
`.xctestrun` configuration.

## Measured native environment API difference

On clean diagnostic source `3409795727b7a9446c3ec943507929046aebbcd5`, one
disposable iOS 27.0 simulator completed its first `launchctl setenv`, but
`simctl getenv DYLD_INSERT_LIBRARIES` still returned the original value. The new
pre-install assertion stopped the run before the CLI was invoked. The native
[receipt](https://github.com/ziahamza/ios-voip-sdk/blob/addd1bf4a2d1abf90133fa6e6224f71f5271d5d4/docs/verification/2026-10-22-runtime-r4/local-3409795-preinstall-readback.json)
has SHA-256 `d2228c811661fc80e85856acf3d6b562c220e447901bb9f3433243e9c2080098`.
Original snapshot hashes were unchanged at cleanup, and an independent bounded
inventory check found no remaining owned simulator, device directory, ownership
file or temporary build.

A separate minimal owned-simulator probe compared both APIs before and after
writing an ordinary marker variable and appending a signed marker library:

- Both APIs reflected the ordinary marker-variable update.
- After the DYLD update, `simctl getenv` retained its baseline hash while
  `simctl spawn … launchctl getenv` returned the exact expected hash and contained
  the owned marker. This establishes an API difference on this measured runtime;
  it does not establish Apple's implementation or an Argent cause.
- `launchctl getenv` returned zero output bytes for an absent key and one newline
  for an explicitly empty key, with exit status zero in both cases. The one-off
  probe's decoder conflated those two values for its otherwise unused marker
  variable; the command-output hashes retain the distinction. That disposable
  simulator was deleted. The permanent parser preserves the distinction.
- Launchctl control processes received only a process-local empty DYLD override.
  The saved global DYLD value was restored through launchctl and verified there.
  Cleanup found zero matching simulators, no device directory and no owned build.

The [cross-API receipt](https://github.com/ziahamza/ios-voip-sdk/blob/addd1bf4a2d1abf90133fa6e6224f71f5271d5d4/docs/verification/2026-10-22-runtime-r4/local-3409795-launchd-cross-api.json)
has SHA-256 `f2dd784eff29b855958e9c65a53d26c135fe418ece38d4ae6891a4f92b61840f`
and binds the one-off probe's source hash. Its original source remains retained
with the ignored local run output. No inherited path is included in either

**Resulting change, native acceptance pending:** the CLI and native fixture now
read current launchd values through `spawn … launchctl getenv`, matching the API
used to write them. Every launchctl control process receives an empty child DYLD
override so a deleted global loader cannot prevent recovery. This override does
not alter saved global values or apply to app launches. The existing CLI journey
also uses launchctl when comparing installation and uninstallation environment.
No timeout or exact-preservation assertion is relaxed.

**Measured offline:** a new stale-`simctl getenv` control first failed because
installation dropped the current inherited library. A separate deleted-loader
control failed when launchctl inherited the missing loader. Both pass with the
fix, alongside the prior ten recovery controls and an explicit absent/empty/
trailing-newline transport case. The fake models the measured API difference;
these controls do not qualify a native simulator OS.

Specification review found that the CLI journey's reader compared stderr as
snapshot data instead of rejecting it. A focused control executes that actual
reader at its external process boundary and first failed when status-zero stderr
was accepted. It now passes: successful reads must have both exit status zero
and empty stderr, matching the CLI and native fixture's readers.
