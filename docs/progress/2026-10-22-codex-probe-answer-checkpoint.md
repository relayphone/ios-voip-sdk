# Incoming-answer probe checkpoint

The runtime discovery probe now waits for the answered call's actual connected state, an empty pending-transaction list and the audio-activation callback before recording `answered`. The successful-request path has a ten-second observation budget; the genuine error path still records its result immediately. The budget is proposed fixture policy, not a platform deadline.

**Measured failure.** [Runtime CI run 39739841429, attempt 2](https://github.com/ziahamza/ios-voip-sdk/actions/runs/39739841429/attempts/2) sampled `answered` at 7530 ms with `connected=false` and one pending transaction. The same answer callback later performed at 8288 ms and fulfilled at 8289 ms. Its synchronous audio configuration precedes fulfillment, but the trace does not separately time the blocking suboperation. The original capture still fails the unchanged state assertion. Its source, artifact digests, selected original rows and limits are preserved in [the classification](../verification/2026-10-22-probe-answer-checkpoint/original-red-classification.json).

**Proposed correction.** Request acceptance does not mean provider fulfillment. Reuse the existing bounded waiter for the actual state and activation handoff. Publish the locked audio-ready flag after writing the activation trace so the readiness predicate implies that callback has been recorded. The gate checks serialized answer → activation → snapshot order; integer millisecond timestamps may tie, and the existing monotonic-clock checks still apply.

**Measured host preparation.** All 98 harness controls pass, including a synthetic timestamp-tie case and a reversed-order rejection. The old gate rejects the timestamp-tie positive; the corrected gate accepts it. The entire probe typechecks against the actual simulator SDK in its existing Swift 5 mode, with warnings retained. [The receipt](../verification/2026-10-22-probe-answer-checkpoint/receipt.json) binds the three changed source files, outputs and compiler inputs.

SPEC and STANDARDS reviews are clear. This is host preparation; a fresh source-bound native runtime discovery run must qualify the corrected checkpoint. No simulator was created or app launched for these checks, and the original red run has not been retried or relabeled.
