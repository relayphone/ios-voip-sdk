# M0 source runtime bootstrap preparation

**Proposed:** the Swift package and Expo pod use the simulator runtime as source targets, rather than an XCFramework. The package is Swift 6 with iOS 17.4 minimum and the target chain `CKSimRuntimeC` → `CKSimRuntime` → `VoIPSDK`. The Expo pod compiles those same source files as one module. `CKLoader.m` is excluded. The runtime C/Swift implementations compile only for iOS simulators; the public facade returns false on devices and other platforms.

Call `SimulatorSupport.activateIfNeeded()` on the main actor **before** creating the process's ConversationManager. Activation has one idempotent attempt per process: success stays active, and refusal stays false. The source path prepares the profile, journal, mailbox and notification with throwing initialization before swapping methods. It restores root, concrete, action-chain and PushKit implementations after refusal, including methods inherited from an already-swapped superclass. It cancels queued simulator work and logs the reason. The standalone loader keeps its constructor and fail-closed refusal policy.

`VERSION` still supplies the C version macro in SwiftPM, the pod and the standalone builder. The canonical behavior profile moved to `Sources/Engine/Resources/ios-27.0.json`; the standalone builder still produces `runtime-dist/profiles/ios-27.0.json`. Source builds detect the PushKit metadata header automatically. SwiftPM resources use `VoIPSDK_CKSimRuntime.bundle`, and the pod uses `IosVoipSDKRuntime.bundle`. The lookup mirrors measured generated app/framework locations and throws when absent; it avoids SwiftPM's generated Bundle.module accessor because that accessor traps when the bundle is missing.

**Measured compile checks:** [saved source/compile metadata](../verification/2026-10-22-sdk-source-bootstrap/). arm64 iOS 17.4 simulator and physical-device Swift package builds succeeded with Xcode 27.1. The source-linked bootstrap regression app builds and signs without injection. A standalone arm64 build succeeded and its packaged profile digest matched the canonical resource. Device inspection found no runtime implementation/private-ABI symbols in the facade product or guarded native engine/interposition objects; the empty Swift module retains ordinary compiler force-load support markers, recorded separately; final linked-device-app inspection remains part of M0 acceptance. Temporary outputs are verification-only and are removed after recording compile metadata.

**Focused native regression, pending execution:** `bash discovery/build_sdk_bootstrap.sh <fresh-directory>` builds `SDKBootstrap.app` without creating a simulator. In a run-owned simulator, launch separate processes with `CKSIM_BOOTSTRAP_CASE=healthy`, `profile` and `push-after-install`, a fresh `CKSIM_RUN_ID`, and no DYLD injection. Capture each through the existing run_scenario.py as `bootstrap-<case>.log`/receipt. `python3 discovery/sdk_bootstrap_conformance.py <capture-directory>` requires bound receipts, a plain source-linked process, healthy idempotence, invalid-profile refusal and exact effective IMP restoration after failure following all CallKit/PushKit swaps. The fault is compiled only in this ABI-testing app.

Five synthetic bootstrap-validator controls passed (positive, failed rollback assertion, injected launch, mixed process and truncated completion). Independent standards, spec and C rollback reviews found no actionable findings. Missing-resource lookup and shutdown guards were tightened during review.

This preparation does not claim M0 acceptance or SDK runtime behavior on a simulator.
