# M3 preparation: system dial requests

**Proposed milestone; native acceptance pending.** This slice is prepared on
M2 core `e466d7f`, with no simulator/device build, launch or dependency download.
It does not mark M3 complete. The acceptance target remains a `tel:` link
opening a dial request in the example after stack integration.

The Swift package gains public URL, user-activity and start-call-intent
forwarding through `VoIPSystemEntryPoints`, plus process-owned
`DialRequestRouter` observation. A resolved public intent supplies one handle
and its video capability; unresolved or multi-recipient requests remain
unhandled. Routing creates no conversation manager or provider.

The Expo subscriber consumes the existing public application callbacks. Expo
58 forwards cold/warm scene URLs and start-call activities into that chain.
The SDK buffers requests until its first actual public JS `dialRequest`
listener attaches, rather than draining on native module creation. A new module
lifetime retires its predecessor; stale generations and teardown cannot reclaim
or remove the newer consumer. Pending requests last for the process lifetime,
without persistent inbox semantics.

The plugin adds opt-in `defaultCallingApp` and its calling-app entitlement,
preserving unrelated entitlements. It registers the public start-call activity
type. The example opts in and displays incoming dial requests without placing
calls. No default-dialer entitlement, EU dialer support, media or provider
backend is added. There is no RFC deviation.
